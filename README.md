# Продажи кофе и погода

Учебное хранилище данных для анализа продаж кофе и погодных условий в 20 городах.
Airflow загружает источники, PySpark создаёт учебные продажи по городам, dbt строит
слои PostgreSQL, ClickHouse хранит витрины, Metabase показывает дашборды.

```text
Kaggle + Open-Meteo -> PostgreSQL raw
Kaggle + города -> PySpark -> raw.synthetic_coffee_sales
raw -> dbt stg -> dbt core -> dbt marts -> ClickHouse -> Metabase
```

Продажи по городам синтетические: исходные покупки Kaggle копируются в города,
а цена рассчитывается как исходная сумма * 10 * коэффициент города.
Это не валютный курс и не реальные продажи российских кофеен. Погодные данные
реальные, но графики на синтетических продажах не доказывают влияние погоды на спрос.

## Требования

- Docker Engine или Docker Desktop с Compose v2.24 или новее.
- Рекомендуется выделить Docker 10-12 ГБ памяти и иметь 15 ГБ свободного места.
- Интернет нужен при первой загрузке образов и для запросов к внешним API.
- Python 3.12+ нужен только для локальной разработки. Основной запуск работает без venv.

## Запуск одной командой

Из корня репозитория:

```bash
docker compose up
```

Для работы в фоне:

```bash
docker compose up -d
```

Compose сам собирает Python-образы и запускает инфраструктуру. При первом запуске:

1. `airflow-init` готовит служебную базу Airflow и локального пользователя.
2. `project-init` восстанавливает учебный снимок RAW только в пустую базу.
3. dbt создаёт stg, core и три витрины, затем выполняет проверки данных.
4. Витрины публикуются в ClickHouse с проверкой количества строк, сумм и ключей.
5. `metabase-init` настраивает новую Metabase и импортирует сохранённые графики.

Первый запуск может занять несколько минут. Контейнеры `airflow-init`, `project-init`
и `metabase-init` после успешной подготовки завершаются с кодом 0: это нормально.

```bash
docker compose ps -a
docker compose logs -f project-init metabase-init
```

Существующий RAW не перезаписывается. Если RAW уже есть, но не хватает необходимых
таблиц, инициализация остановится с понятной ошибкой вместо частичного смешивания данных.
Существующие аккаунты и дашборды Metabase сохраняются без изменений.

Остановка без удаления данных:

```bash
docker compose down
```

Не добавляйте `-v`, если нужно сохранить базы и дашборды: этот флаг удаляет Docker volumes.
После изменения Dockerfile или зависимостей используйте `docker compose up --build -d`.

## Локальные зависимости и venv

Установка всех зависимостей для локального dbt и тестов одной командой:

```bash
bash scripts/setup.sh
```

Скрипт создаёт `venv`, устанавливает `requirements-dev.txt` и копирует `.env.example`
в `.env`, только если `.env` ещё нет. Зависимости Airflow и Spark устанавливаются
в контейнерах, а не в это окружение.

Активация:

```bash
source venv/bin/activate
```

Выход: `deactivate`.

`.env` необязателен для демонстрационного запуска. В нём можно переопределить порты,
пароли и Kaggle-токен. Порт DWH на хосте и внутри Docker различается: `5433` и `5432`.

## Подключения

Значения по умолчанию для **новой локальной установки**:

| Сервис | Адрес | Пользователь | Пароль | База |
|---|---|---|---|---|
| Airflow | http://localhost:8080 | `airflow` | `airflow` | - |
| PostgreSQL DWH | `localhost:5433` | `dwh` | `dwh` | `dwh` |
| ClickHouse HTTP / DBeaver | `localhost:8123` | `analytics` | `analytics` | `marts` |
| ClickHouse native | `localhost:9000` | `analytics` | `analytics` | `marts` |
| Metabase | http://localhost:3000 | `admin@example.com` | `WeatherDemo2026!` | - |
| Spark master UI | http://localhost:8082 | не требуется | - | - |
| Spark worker UI | http://localhost:8083 | не требуется | - | - |
| Spark application UI | http://localhost:4040, пока работает задание | не требуется | - | - |

В Metabase подключение уже настроено: `clickhouse:8123`, база `marts`.
Из контейнеров PostgreSQL доступен как `dwh-postgres:5432`.

Служебные PostgreSQL не публикуют порты на хост:

| Назначение | Хост внутри Docker | База / пользователь / пароль |
|---|---|---|
| Метаданные Airflow | `airflow-db:5432` | `airflow` / `airflow` / `airflow` |
| Метаданные Metabase | `metabase-db:5432` | `metabase` / `metabase` / `metabase` |

Redis доступен только внутри Docker как `redis:6379`, без пароля.

Если используются существующие volumes или собственный `.env`, действуют ранее
созданные учётные записи. Автоматическая подготовка не сбрасывает их пароли.
Все демонстрационные пароли и ключи публичные: проект нельзя публиковать в интернет
без отдельной настройки аутентификации, секретов и сетевого доступа.

## Данные и дашборды у другого пользователя

`demo/raw/` содержит сжатый снимок пяти таблиц RAW и контрольные суммы файлов.
Это данные проекта, а не дампы системных баз. Внешние API и Kaggle-токен не нужны,
чтобы впервые увидеть те же исторические графики.

`demo/dashboards.json` содержит определения 15 активных вопросов и трёх дашбордов:

- Продажи и погода.
- Ассортимент и продажи.
- Дневные продажи: сезонность и погодные условия.

Импорт сопоставляет таблицы и поля по именам: внутренние ID Metabase на другом
компьютере могут отличаться. Пользователи, пароли, сессии и пример E-commerce
из стандартной Metabase не экспортируются. Архивные вопросы не восстанавливаются.
Пользовательские запросы и расположение карточек сохраняются как есть.

После создания новых графиков обновите экспорт из корня проекта:

```bash
python3 scripts/export_demo.py
```

Экспорт читает работающие контейнеры и обновляет `demo/`, но не меняет базы.
После этого добавьте обновлённые файлы `demo/` в свой коммит.
Автоимпорт предназначен для новой установки и не заменяет уже отредактированные
дашборды при каждом перезапуске.

## DAG-и

| DAG | Расписание | Назначение |
|---|---|---|
| `load_kaggle_coffee` | вручную | Однократная загрузка исходных продаж; заполненная таблица пропускается |
| `weather_history_backfill` | вручную | Архив погоды; параметры `start_date` и `end_date` задают период |
| `weather_forecast_hourly` | каждый час | Новый снимок трёхдневного прогноза в RAW |
| `publish_marts_to_clickhouse` | на 20-й минуте каждого часа | dbt build с тестами и публикация трёх витрин |

Время расписаний Airflow: UTC. Продажи Kaggle исторические и не увеличиваются сами.
Архив погоды обновляется ручным backfill; получение прогноза не обновляет архив.
Существующие DAG-и сохраняют выбранное пользователем состояние паузы.

Публикация пишет во временную таблицу ClickHouse, проверяет данные и только после
успеха атомарно заменяет соответствующую рабочую таблицу. Повторная публикация
не добавляет дубликаты. Ошибка dbt или тестов блокирует этап публикации.
Три таблицы заменяются по отдельности, не общей транзакцией.

Новая витрина требует SQL-модели dbt, описания в `dags/config/marts.json`
и DDL в `dags/sql/clickhouse/`. Произвольные SQL-файлы автоматически не исполняются.

## Spark

Профили городов: `spark/jobs/config/city_sales_profiles.csv`.
Проверить преобразование без повторной записи существующей таблицы:

```bash
docker compose exec spark-client /opt/spark/bin/spark-submit /opt/spark/jobs/scale_sales.py --check-only
```

Создание `raw.synthetic_coffee_sales` в базе, где этой таблицы ещё нет:

```bash
docker compose exec spark-client /opt/spark/bin/spark-submit /opt/spark/jobs/scale_sales.py
```

Режим записи намеренно не перезаписывает существующую таблицу. В комплектном снимке
она уже заполнена, поэтому для обычного запуска повторять генерацию не нужно.

## dbt и проверки

Все модели и тесты в контейнере:

```bash
docker compose exec dbt dbt build
```

Только проверки уже построенных данных:

```bash
docker compose exec dbt dbt test
```

Локально, после активации venv:

```bash
cd dbt/my_dwh
export DBT_POSTGRES_HOST=localhost
export DBT_POSTGRES_PORT=5433
dbt deps --profiles-dir .
dbt build --profiles-dir .
```

При нестандартных реквизитах задайте также `DWH_POSTGRES_USER`,
`DWH_POSTGRES_PASSWORD`, `DWH_POSTGRES_DB`.

Проверяются уникальность составных ключей, заполненность обязательных полей,
ссылки на справочники, диапазоны значений, местная дата продажи, равенство суммы
позиций сумме чека и сохранение выручки и числа продаж в витринах.
Отсутствующие погодные показатели допустимы и не заменяются нулём.

Python-тесты:

```bash
python -m unittest discover -s tests -v
```

GitHub Actions запускается при pull request `dev -> main`: проверяет Compose,
Python, конфигурацию витрин, восстанавливает учебный RAW в отдельный PostgreSQL,
затем выполняет настоящий `dbt build` с тестами. Ошибки не игнорируются.
CI не использует ваши `.env`, пароли или рабочие базы.

## Источники и научная основа

- [Kaggle: Coffee Sales Dataset, navjotkaushal](https://www.kaggle.com/datasets/navjotkaushal/coffee-sales-dataset/data): исходные покупки кофе. При повторном распространении данных учитывайте лицензию, указанную автором на Kaggle; лицензия кода проекта не заменяет лицензию датасета.
- [Open-Meteo Forecast API](https://open-meteo.com/en/docs?forecast_days=3&hourly=temperature_2m,apparent_temperature,precipitation): почасовой прогноз. Дополнительно используются давление и вероятность осадков.
- [Open-Meteo Historical Weather API](https://open-meteo.com/en/docs/historical-weather-api): историческая погода. Исторические значения являются данными погодных моделей/реанализа, а не измерениями собственных датчиков.
- [The Relationship between Weather and Meal choices: A Case Study of Restaurants and Cafés on Korean University Campus](https://www.kci.go.kr/kciportal/ci/sereArticleSearch/ciSereArtiView.kci?sereArticleSearchBean.artiId=ART002912626): научная основа постановки вопроса о связи погоды и выбора еды/напитков.
- [Исследование прогнозирования потребления кофе с учётом погоды и состояния воздуха](https://www.kci.go.kr/kciportal/ci/sereArticleSearch/ciSereArtiView.kci?sereArticleSearchBean.artiId=ART002977698): дополнительная научная работа по тематике проекта.

Статьи использовались как научный контекст. Проект не воспроизводит их эксперименты,
не переносит их выводы на синтетический датасет и не собирает показатели качества воздуха.

## Ограничения аналитики

- Во всех городах повторяется исходная последовательность покупок, а цены заданы коэффициентами.
- Сейчас один учебный чек содержит одну позицию и одну единицу товара.
- Дневная витрина содержит только дни с продажами; её средние нельзя трактовать как средние по всем календарным дням.
- Для сравнения погоды учитывайте полноту дня: `temperature_hours_count` и `precipitation_hours_count`.
- Общий средний чек: сумма выручки / сумма числа чеков. Средние и проценты по дням нельзя просто складывать.
- Нет себестоимости и счётчика посетителей: выручка не равна прибыли, число чеков не равно трафику.
- Снимок прогноза в `demo/` исторический. Проверка свежести источника имеет смысл после новой загрузки API.
